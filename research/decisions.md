## D009: 约束证据数量与 Git 保存边界

提出日期：2026-10-07。
状态：`proposed`。
来源：用户担心 baseline 产生 835 项工作区变更，因不确定保存边界而尚未在 propose 后提交。研究侧只读盘点：835 项中 780 个文件属于 24 个 run（8 个模型运行、16 个分析检查，跨 `-001`/`-002` 两版）；其中 192 个源码快照文件、232 个二进制产物，run 总内容 76,206,301 bytes，源码快照 2,244,876 bytes；run 之外 55 项。数字截至本轮维护之前，既有 tracked 删除也有 untracked 新文件，不等于 835 份独立研究结论。

观察：保存预测/标签/参数及旧版本有必要，但证据要求尚缺默认去重规则、保留粒度和 Git 收纳边界。现有 skill 允许包或外部持久存储，项目协议第 6.1 节更已指定小规模产物打包校验后入库；这次尚未做保存收尾，展开目录全暴露给 Git 状态。Git 会去重相同内容的 blob，文件数不等于同等比例的历史体积增长，但目录和审阅负担仍存在。

候选建议：

- 当前代码、README、规格、OpenSpec 归档和权威研究记录按路径明确提交；运行证据沿用现有“小型封存包 + 包外 SHA256 + 可读摘要/来源 + 外部索引”，完整保留两版，避免把完整展开目录和相同内容的包同时入库。
- 清单/索引指向经核验的持久产物后，再确定展开目录的忽略范围；忽略本身不算保存或备份。较大产物另定持久存储，不自动上传。
- 后续流程明确开发核验与正式 run 的保留粒度。能用临时 fixture 完成的检查继续使用临时目录；需持久保留的分析记录以问题为单位组织，引用输入 run。不能为了减少文件静默丢弃规范要求的产物。
- 后续实现可按源码内容身份共享快照，但需保存可恢复内容并有独立验证；只存哈希不足以恢复未提交代码。这属于新实现范围，不在本轮修改已核验代码或旧 run。
