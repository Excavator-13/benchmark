# research-maintainer 为什么要改、怎么改

日期：2026-10-08。
性质：修改建议。本文件不修改现有 skill、科研协议、实验产物或 Git 历史。

历史提案：形成于新版 skill 审查之前。后续审查见 [maintenance review](20261008-maintenance-and-protocol.md)，已接受的项目政策见 [D010](../decisions.md#d010-采用实验记录与保存减负政策)；本页不作为现行规范。

## 1. 要解决什么问题

r-m 的工作应当是让下一次科研能接着做：知道研究问题、任务进度、实验条件、主要结果、未决问题和下一步。

2026-10-07 的实际体验是：用户已经要求提交、push 并结束一天的工作，agent 却继续取回远端材料、尝试独立 checkout、做恢复核验，最后需要用户主动叫停。记录维护开始消耗本来应该用于科研或休息的时间。

**我们需要足够清楚的科研记录，不需要把每次收尾做成一次存储系统验收。**

## 2. 为什么现有设计容易过度执行

### 2.1 职责混在一起

[SKILL.md](../../.agents/skills/research-maintainer/SKILL.md)和 [archive-and-git.md](../../.agents/skills/research-maintainer/references/archive-and-git.md)同时覆盖科研交接、运行来源、封存、Git 入库、异地备份和恢复。这些动作的成本差别很大，却共用一套“收尾”入口。

“记录文件保存在哪里”逐渐变成了“负责证明这些文件已经完整保存、可以从远端恢复”。后者已经超出科研记录维护的职责。

现有规则没有强制每次 push 后都做恢复测试。我把“没有做过恢复测试就不要声称做过”扩大成了“结束前必须做一次恢复测试”，这是具体的执行错误。修改 skill 要同时去掉促成这种扩张的职责和默认流程。

### 2.2 证据要求缺少成本边界

baseline 曾产生 835 项工作区变更，其中 780 个文件来自 24 个 run，包含 192 个源码快照文件和 232 个二进制产物。原始记录见 [D009](../decisions.md#d009-约束证据数量与-git-保存边界)。

这些文件主要由 baseline runner 和 OpenSpec 执行、修复过程产生，不能全部归因于 r-m。预测、标签、参数和修复前后的运行也确实可能需要保留。

问题在于：r-m 没有明确“引用已有证据即可”“普通检查不必成为独立科研 run”“记录规模应与研究问题相称”。模板和证据要求容易被执行成每项操作都要完整留档，重复已有实现和验证流程的工作。

### 2.3 没有清楚的结束条件

已有规则强调不能把未知写成成功，却没有同样明确地强调：**如实记录未知，本身就可以完成交接。**

于是“未核验”容易变成新任务；push 后更新索引、再提交、再同步又容易变成额外收尾。用户要结束工作，agent 却不断发现还能做的检查。

## 3. 新的职责边界

建议把 r-m 定义为：**科研状态与实验来源的轻量记录维护者。**

| 范围 | r-m 应当做什么 |
| --- | --- |
| 研究方向 | 维护目标、阶段、任务及其真实完成情况 |
| 科研交接 | 记录做到哪里、结果在哪里、下一步是什么 |
| 科研判断 | 区分观察、解释、建议与已经接受的决定 |
| 实验来源 | 记录运行所基于的 commit、相关未提交改动、配置、数据及必要环境信息 |
| 实验结果 | 引用现有摘要、日志和关键产物，记录结论与限制 |
| 文件位置 | 记录实际路径；移动或保存位置已改变时更新指针 |
| 代码实现与独立验证 | 交给项目已有流程，r-m 引用其结果，不重复执行 |
| commit、push、打包、备份、恢复演练 | 移出 r-m 的默认职责，按用户具体请求处理 |

用户在 r-m 会话中明确要求 commit/push 时，同一个 agent 仍可执行普通 Git 操作，不必换会话或另造一个 Git skill。但 r-m 不能给这个请求附加封存、下载、全新 clone、恢复演练或额外回执要求。

读取 commit 或相关工作区差异，是为了确定实验来源；不因此扩展到审计远端引用和备份状态。

## 4. 具体怎么改

### 4.1 收窄 SKILL.md

- description 聚焦研究计划、进度、决定、实验来源和交接，移除备份管理职责。
- 删除默认路由中的“提交、推送、恢复”工作流。
- 将“运行、封存、提交和备份分别记录”改为“科研完成按任务验收判断；已知的保存位置按事实记录”。
- 收尾默认只要求必要的研究记录更新，不默认要求打包、包外清单、Git 入库或远端恢复核验。
- 保留来源 commit 不随 HEAD 改写、重要结果不可凭聊天推断、旧封存材料不被静默覆盖等规则。

### 4.2 删除 Git 管理参考，保留实验来源说明

建议用简短的 `experiment-provenance.md` 替代当前 `archive-and-git.md`。它只解释：

1. 运行基准 commit 是历史身份，不是当前 HEAD，也不是后来保存产物的 commit。
2. 执行代码有未提交改动时，记录影响本次实验的差异或脚本；已有 runner 保存了来源时直接引用。
3. 配置、数据、关键环境和结果位置需要能识别，不要求每次复制整个仓库或建立全量哈希体系。
4. 原记录有缺失时如实注明，不追溯伪造、不自动重跑。

从 r-m 中移除 commit/push 操作步骤、远端取回要求、备份回执、恢复演练及封存包验收流程。用户确实要求这些工作时，按该次请求和项目实际需要执行。

### 4.3 减轻 records.md 的默认负担

- 保留入口、阶段计划、state、decisions 的职责划分，避免重复进度表。
- run 模板按实验类型使用，不要求每轮维护、每次检查、每条分析命令都新建 run。
- 正式实验保存哪些产物，由研究协议和 runner 决定；r-m 不再叠加一套强制产物清单。
- 普通分析可以在现有任务记录中保存问题、命令或脚本位置、结果和限制；只有值得独立追踪的工作才建新 run。
- 产物索引以“实验或 run、用途、摘要、实际位置”为主，SHA256、入库身份、备份核验字段仅在确有用途时附加。
- 不把所有模板字段都视为必须完成的事项，不为填写空字段制造新工作。

重要科研材料仍要保留。例如比较预测误差时，必要的预测、标签和节点身份不能因为简化文档就丢掉。这里减少的是记录流程的重复劳动。

### 4.4 给 transitions.md 增加明确的停止规则

建议直接写入以下规则：

> 普通交接完成于：当前任务位置、主要结果、必要证据位置、未解决问题和下一动作已记录。未知事项可以保持未知，不自动升级为阻塞或待办。
>
> 用户明确要求 commit/push 时，按范围提交并推送；push 成功即完成该请求。只有用户要求恢复核验，才执行远端下载或恢复演练。
>
> 用户要求结束或停止时，停止本轮自行启动的额外检查，保存必要的科研恢复点并结束。不得把取消的检查改写成以后必须补做的任务。真正仍在运行的实验另按用户指示处理。
>
> 收尾记录以实用为准，不为了记录记录自己的提交、推送身份而无限追加文档提交。

### 4.5 整理仓库中与新边界冲突的文字

修改 skill 后还需要同步检查 [AGENTS.md](../../AGENTS.md)、[DELEGATION.md](../../DELEGATION.md)、科研入口和记录模板，清除把封存、提交、备份核验交给 r-m 的职责描述，否则新旧规则会继续打架。

保留 OpenSpec 的独立验证职责、研究侧验收和委托指针的单一写入者规则。r-m 应消费已有核验结论；如发现具体冲突，就记录或交回对应流程，不自动重复整套验证。

本项目[协议第 6.1 节](../phases/P01/protocol.md#61-实验记录与产物保存)在本提案形成时另有打包入库约定。后续需要明确其适用范围，不能仅修改 skill 就声称这些约定已失效，也不能把它当作所有科研维护的通用规则。（当前链接指向 D010 更新后的政策；本段保留历史建议。）

已封存的包、旧运行来源和历史记录保持原样。职责调整不需要重新整理、重算或“修复”昨天的全部材料。

## 5. 用什么判断改对了

修改后的行为应满足这些常见场景：

| 用户请求 | 应有行为 |
| --- | --- |
| “更新科研状态” | 读当前计划和相关结果，更新必要记录，报告下一步；不自动打包或做 Git 操作 |
| “记录这次实验” | 记录问题、条件、来源 commit、关键结果和产物位置；已有来源材料直接引用 |
| “commit、push，今天结束” | 检查提交范围，提交并 push，简短报告后结束；不自动下载或 clone |
| “这个结果还不能完整复现” | 记录具体缺失；除非影响当前科研判断或用户要求处理，不阻止交接 |
| “核验备份是否能恢复” | 这时才按明确范围执行恢复检查 |
| “停，不检查了” | 停止额外检查，记录取消，不安排下次自动续跑 |

**修改目标：下一次能继续科研，这一次能正常结束。记录成本要与科研问题相称。**
