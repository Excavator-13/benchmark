# 科研记录与实验协议减负方案

日期：2026-10-08。状态：**项目政策、第一轮整理、baseline 实现与研究侧验收均已完成**；可选第二轮迁移仍保留为候选。
原文是审查与提案，以下 §1–8 保留提出时的论证；其“尚未采用/未执行”描述该时点。后续接受依据为 [D010](../decisions.md#d010-采用实验记录与保存减负政策)，实际修改和下一动作见 §9。skill 修订由维护者完成，本轮不再修改 skill。

## 1. 判断

**更新后的 r-m 没有因这次修改遭受重大功能损失，也没有严重冗杂化。证据膨胀的主要来源是项目协议、baseline 规格及其实现把不同性质的工作统一当成了完整运行。**

835 项变更本身不能证明 skill 设计失败，但它说明记录粒度与科研目的不匹配。昨天的 780 个产物文件来自 24 个 run：8 个模型运行、16 个分析检查，跨两版实现；其中 192 个源码快照文件、232 个二进制产物。统计来源是 [D009](../decisions.md#d009-约束证据数量与-git-保存边界)，不是本轮重新做了一套哈希审计。

应保留的核心是：能知道实验回答什么问题、用什么代码和条件、怎样执行、得到什么结果，以及结果支持什么判断。每条检查命令、每次交接和每次 push 都不需要拥有一套同等级的来源与归档体系。

### 2.2 保留了什么，改好了什么

研究方向、任务/阶段验收、单一权威记录、建议与接受决定的区分、来源 commit 的历史身份、脏源码的真实来源、封存材料不被覆盖、中断恢复和授权边界均保留。更新以增补边界为主，没有把 r-m 缩成只记录 commit 的工具。

建议维持这版职责结构，只修上述少量问题。此前的 [skill 改造建议](20261008-research-maintainer-redesign.md)是历史建议，本报告结合维护者的实际修改重新判断，不要求其完全接受此前方案。

## 4. 新协议的原则

### 4.1 按研究对象记录，不按命令次数记录

| 工作 | 怎样记录 |
| --- | --- |
| 模型实验、消融、改变条件的受控诊断、实际时间回测 | 进入 `research/runs/<run-id>/`，保存实验材料 |
| 为科学重复性实际重新执行模型 | 保留独立执行身份和输出，可归入同一实验系列；不把重复运行压成一次 |
| 用已保存预测重算指标、比较两次执行、核对旧 gold | 保存输入 run ID、检查脚本/代码版本、命令、结果、容差及必要输入身份；归属被检查实验或 OpenSpec 报告，无独立完整 run |
| 新分层分析、图分布分析等独立科研分析 | 保存问题、脚本/来源版本、输入版本、步骤、表/图及限制。可有独立分析文档；若它本身执行受控干预或产生新预测，再按实验记录 |
| 单元测试、临时 fixture、失败的开发探针 | 使用临时/忽略目录；有用的失败原因进入开发报告，不进入正式实验目录 |
| 状态更新、委托回收、skill 审查、建议、commit/push | 文档或正常 Git 记录；无 run、无实验归档包 |

是否训练不是唯一判据：确定性朴素 baseline 也是实验。相反，调用了 Python 或读取了真实数据，并不自动成为完整实验。科学结论仍须有可复查的分析过程；减负不能把关键分析只剩成一句聊天里的数字。

### 4.2 科学要求保持

保留当前节点/时间身份与不跨界划分、L=6/H=3、训练期拟合标准化、验证集选参照和 lambda、测试集不参与选择、预先定义的活跃度/邻居分组、总体/分组完整报告、原始单位与裁剪结果区分，以及公平对照与结论限制。

保留 §6.2 同条件重复、确定性方法不制造 seed 方差、配对收益与图对照、§8 开发回测，以及不把节点/重叠窗口当独立统计样本的约束。这些关乎科学判断，本提案不因嫌文件多而删除它们。若日后需要调整实验数量或收益门槛，应另行论证。

### 4.3 材料适量，来源足够

一次实验应有摘要、来源与配置、执行步骤和结果。commit 已覆盖的源码/协议无需逐次复制；保存 commit 和相对路径即可。执行所需依赖和关键运行条件仍要记录。

若执行源码有未提交改动，仅保存影响实验的 patch 和必要未跟踪源码；不能只记 HEAD 后声称完整来源，也无需复制整个仓库、测试目录或所有规划文档。共享同一脏源码快照时可引用一次内容，复杂去重系统不是本轮前置条件。

输入数据版本/哈希可共享已保存的数据清单；节点、时间、gold、固定掩码可由同一数据/协议的多个方法共用。保存被报告方法的预测、被选模型参数/预处理统计、全部候选的验证分数与选择理由。落选候选的完整预测和参数默认不长期保留；若研究问题需要它们，再明确保存。

压缩数组可以合并文件，但关键是减少重复对象，不为追求极少文件引入难以读取的新格式。无需增加数据库、自动证据图或多级签名体系。

## 5. 可直接采用的协议文字草案

以下用于替换 §6.1；尚未写入现行协议。

> ### 6.1 实验记录与产物保存
>
> 本节的完整产物要求适用于模型实验、受控诊断和时间回测，不适用于每条命令、普通检查、软件测试或记录维护。一次实验围绕明确研究问题和执行条件组织，可包含多个方法与多条步骤；需要比较的独立重复执行保留各自身份和结果。
>
> 实验使用独立且不覆盖旧结果的 `research/runs/<run-id>/`。至少记录：目的与所属任务；执行代码 commit 及影响实验的未提交差异/必要脚本；科学协议版本与可定位内容；数据版本或内容身份；解析后的配置、关键环境、准确命令和实际步骤；成功/失败/中断状态；主要结果与限制。
>
> 正式预测结果还须保存足以重算所报告指标的预测、标签、节点/时间/划分身份、固定分组掩码，以及被选模型参数、必要预处理统计和训练/选模记录。多个方法可共享标签和身份。保留全部候选的验证分数与选择理由；落选候选的完整参数和预测仅在研究需要时保留。
>
> Git 中已有的源码和协议以 commit 加相对路径定位，不要求每次复制。共享的数据清单和来源材料允许引用；引用须指向固定版本。未提交的相关执行代码必须保存可恢复内容。材料缺失时记录对复现和结论的具体限制，不追溯伪造。
>
> 指标重算、重复结果比较、旧结果对齐等检查保存简洁报告，包含被检查对象、检查脚本/来源版本、命令、结果和必要容差。开发检查由开发/验证记录承载，实验检查归属相应实验。检查不自动创建独立科研 run，不复制完整实验来源和环境。不覆盖封存材料；后续检查报告放在外部并链接原实验。
>
> 实验材料可直接以文件保留，也可在确有需要时打包。小型摘要、配置、指标、选择记录及必要产物可以纳入 Git；大型产物按已确定的持久存储位置保存并在索引记录位置。临时开发输出留在忽略目录，不因执行过一次就永久收纳。失败/中断实验保留已形成的记录和有价值产物；普通开发失败无需完整封存。
>
> 实验完成按执行与科研验收判断，不以打包、逐文件校验、commit、push 或远端恢复演练为完成条件。支持正式结论的必要材料应保存在明确位置；只有本机副本时如实说明存储风险，不冒称已有异地备份。Git 和备份动作按用户授权进行，push 请求在正常推送成功后结束。封存旧包保持不变，恢复核验仅按明确请求执行。

同步修改 §9 “保存可恢复”一行，建议改名为“研究材料可定位”：

> 支持阶段结论的必要来源、配置、执行过程、结果和重算材料有明确保存位置；缺失和存储限制已说明。科学验收不附带打包、Git 同步或恢复演练的完成条件。

原“正式实验入口尚待开发”及指导第 401 行也应更新为当前已有入口，避免新 agent 再从旧建议重新开始。

## 6. 怎么落实，怎样算完成

这不是只改 skill 能解决的事情。建议在决定采用方案后，由研究侧记录存储政策调整，再用现有 OpenSpec 流程修改主规格和实现。科学协议版本与记录格式版本需区分；若只调整保存方式，明确科学定义仍与 v3 兼容，旧实验不为格式变化重跑。

| 修改对象 | 具体变更 |
| --- | --- |
| `research/phases/P01/protocol.md`、`plan.md` | 收窄 §6.1 适用范围及保存完成条件；计划引用新政策，历史验收事实保留 |
| `execution-guide.md`、archive index 的“新记录”说明 | 更新已过时入口描述；诊断只留必要报告；移除默认全量包/校验/提交流水线，索引承担位置而非检查待办 |
| `openspec/specs/nograph-baseline-entry/spec.md` | 替换“每个调用”“分析命令 fresh check run”的强制要求；保留重算能力、重复执行与完整科学指标，独立验证仍独立进行 |
| baseline runner/artifacts | 分清正式实验与开发调用；只捕获相关运行源码差异；已有已提交源码不复制；落选候选默认只留选择表 |
| baseline checks/CLI | 支持明确报告输出路径，不强制完整 RunDirectory；报告能链接输入实验与检查来源，不能改写旧结果 |
| `.gitignore` 与当前说明 | 给开发输出一个稳定忽略位置，例如根目录 `scratch/`；未来 curated 实验在既有 `research/runs/`，替代每轮手写 24 组精确例外 |

不需要为这项减负建立新的复杂框架。接受后的实现验收用少量有代表性的情况即可：开发 fixture 不生成正式 run；指标检查只产生报告；正式模型结果依然可从保存数组重算；dirty execution source 能定位；旧包未改；push 后没有自动恢复演练。r-m 本轮不会注册或执行新的实现委托。

## 7. 现有仓库可以怎样净化

**可以，先整理当前视图和重复副本，再决定要不要移动历史目录。无需重新封存、重训或改写 Git 历史。** 昨天的 24 个包已包含全部 780 个文件；原始内容和保存核验事实见[索引](../archives/index.md#t004-baseline-运行2026-10-07)。本提案沿用已记录事实，不恢复那项已取消的远端检查。

### 7.1 第一轮：收益明确，改动少

| 已有材料 | 推荐处理 | 约束与效果 |
| --- | --- | --- |
| 24 个 `.tar.gz`、配套 SHA256、总清单 | 保持原样，作为旧格式历史材料 | 新规则不要求旧材料“合规重制” |
| 88 个已跟踪的 summary/provenance/command/report | 保留可读记录；索引按“当前实验 / 历史模型运行 / 关联开发检查”展示 | `-002` 的四个模型执行是当前 T004 依据；`-001` 四个模型执行是历史；16 个检查不再在未来政策中充当完整实验 |

“清理展开副本”不是删除整个 run 目录。summary/provenance 等可读入口仍要在；现有 checker 默认从展开数组读取，清理后使用者须从包恢复到独立目录并指定对应输入。`seal_20261007_baseline.py` 的 seal 路径依赖展开材料，清理后不能把重新 seal 当默认操作。索引需简短说明此变化，不重写旧包内绝对路径或旧核验报告。

### 7.2 第二轮：按职责收拢零散历史

### 7.3 不能靠新协议直接删掉的东西

## 8. 推荐顺序

先采用“实验完整、检查简洁、维护只写必要文档”的分类与 §6.1 保存政策；让 baseline 规格和实现遵循它，阻止新膨胀。再做第一轮净化；第二轮历史迁移可以稍后进行，不阻塞科研。
