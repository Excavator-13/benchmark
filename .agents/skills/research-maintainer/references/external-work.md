# 外部、人工与其他流程执行

本文件处理两种“执行不在本会话完成”的情况：由人或另一台机器按文档执行，以及把实现、验证或评审交给另一套流程。两者的共同点是交接必须靠文件而不是聊天。只在这类情况出现时阅读。

## 外部或人工执行

当实验在另一台机器、集群、云实例或合作者手中执行，本会话只负责准备、接收和验收时：

1. **写执行指导，而不是聊天里的命令。** 指导至少包含：本轮回答什么问题、做到哪里停止；冻结条件（源码基准、数据、配置、seed、选模、指标口径）；执行前检查及其判定方式；结果判断与下一动作对照；回填模板。指导是执行接口，不是科学协议；协议仍以快照为准。
2. **预检要能产出 pass/fail。** 能脚本化的检查写成脚本并输出机器可读的结果文件（例如 `preflight.json`），而不是在正文里写“请确认”。断言失败时停止，不带着未解释的差异开始正式执行。
3. **写明本页的核验范围。** 指导末尾说明哪些段落编写时已检查、哪些尚未实机执行（例如“GPU 段与传输未实机核验”）。这不是免责声明，而是让下一位执行者知道该重点核对什么；首次实机暴露的缺陷在指导中打日期注，并说明对已完成 run 的影响。
4. **指导随 run 保存实际使用版本。** 执行中必须改指导时，打日期注说明改了什么、从哪个 run 起生效；已完成或失败的 run 保留其使用的版本，不用新指导覆盖旧 run 记录。指导不承载结果叙述——结果写在 run summary。
5. **回传内容结构化。** 至少包含：run ID、summary、状态与退出码、预检结果、选择与成本记录、与前次运行比较的结果、未决问题。取回材料后先确认清单存在，再更新记录；传输成功不等于已入库、已封存或已备份。
6. **复跑要写条件可比性判定。** 当一次执行声称重复、复现或对齐另一个 run 时，记录必须给出结论：`可比 / 有条件可比 / 不可比`，附证据（源码、数据、依赖、设备）与无法解释的差异，并说明该差异如何影响解释。结论与证据写进 run 记录，不只写在聊天里。本地复跑同样适用。

对应记录：指导放在阶段或其他稳定位置（如 `phases/<phase>/<topic>-guide.md`），阶段计划或任务行链接它；run 目录保存实际使用的指导副本、预检结果、条件核对和执行说明；state 写“等待外部执行”或“已回传”，不把“指导已写好”写成“实验已开始”。

## 交给其他流程执行

研究侧常把实现、独立验证或评审交给另一套流程、另一个会话或另一个人。此时需要的是一条指针，不是第二张进度表。

- **登记时机是工作真正启动**，不是计划冻结的时候。计划里预留的对象名、待办事项的标题都不是在途委托；把“计划要做什么”登记成“已经交出去了”，会让两侧都出现假状态。
- **指针只记**：对象名、研究任务 ID、结束判据，以及回收时欠的研究侧收尾。对象名只记名字，不记路径（对方可能在归档时移动或加前缀）。不记对方的任务勾选、阶段进度或内部设计。
- **单一写入者**：只由研究侧写，对方流程既不读也不写。方向固定，避免双方互相覆盖。
- **同时最多一条在途**；历史由版本历史承担，不在指针里保留旧条目。
- **研究侧只做只读核对**：按结束判据检查是否完成；未完成就提醒，不代跑对方的流程，不改代码、不移目录、不代替对方提交或推送。已完成时做研究侧收尾并关闭指针。
- **对方的 PASS 或报告是证据，不是验收**。研究验收仍按本 skill 的任务验收判断；实现就绪不等于实验完成。
- 指针文件的位置和名称由项目决定；规则放在项目入口文件里，可变状态放在单独文件中，两者不混。

## 边界

准备指导、登记指针、接收和验收材料属于记录维护范围；启动外部机器、调用对方流程、替对方提交或推送需要各自的授权。完成一次回传或回收即结束本轮，不追加对方流程的检查，也不把未做的核对写成待办。
